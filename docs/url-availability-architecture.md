# URL Availability Architecture

Chinese version: `docs/url-availability-architecture.zh-CN.md`.

This document records how URL availability is implemented today and what should
be changed before the next major rewrite. The current system works, but it was
built through several independent patches. Treat this document as the map before
touching the code.

## Current State

There is no single canonical availability engine today.

The repository currently has three different meanings that are all displayed as
"available", "unavailable", "expired", or "unknown":

- HTTP probe result: a URL was checked by this repository with `HEAD` or a
  ranged `GET`.
- Upstream archive status: an external archive or mirror source says the
  original URL was available or unavailable when that archive saw it.
- Metadata-derived availability: a source record has a size, timestamp, mirror,
  or other metadata that implies the URL is probably usable.

These meanings are valid, but they should not be mixed silently.

## Cross-Cutting URL Health Index

The cross-cutting health index is generated by:

```bash
python scripts/probe_url_status.py
```

It writes:

```text
outputs/url_status.json
```

The output is intentionally outside the published `docs/` directory. The script
scans JSON files under `docs/data/`, except:

- `docs/data/android/lists/`

It recursively collects HTTP links from fields named:

- `url`
- `archive_url`

It intentionally skips fields named `urls`. This matters for WuWa because WuWa
file records can contain a primary `url` plus a multi-CDN `urls` array. The
current health index checks the primary URL, not every alternate CDN URL.

WuWa multi-CDN availability is now handled by the WuWa availability build step,
not by `url_status.json`. `scripts/build_wuwa_availability.py --live-probe`
uses the shared `url_probe.py` primitive through `probe_scheduler.py`, probes
candidate URLs with bounded fallback, and writes the resulting facts into WuWa
version/list JSON. The cross-cutting `url_status.json` remains an offline audit
index and must not be treated as the frontend source of truth for WuWa CDN
selection.

For each selected URL, the probe logic is:

1. Try `HEAD`.
2. If `HEAD` is blocked, empty, or suspicious, try `GET` with
   `Range: bytes=0-0`.
3. Record status, final URL, content type, size, last modified, ETag, error,
   and `ok`.

The result is considered `ok` when the response is in the `200..399` range and
does not look like an empty HTML error page.

The probe is incremental by default:

- New URLs are always probed.
- Previously unavailable URLs are re-probed sooner.
- Old healthy URLs are rotated through in batches.
- `URL_STATUS_FORCE_FULL=1` forces a full sweep.

Important limitation: `url_status.json` is not a frontend source of truth. The
page does not load it directly. It is an unpublished offline audit index.

## Android APK Availability

Android APK availability is implemented inside:

```text
scripts/sync_android_apks.py
```

This pipeline has its own availability rules because APK endpoints often behave
differently from normal CDN files.

The Android logic can:

- probe with `HEAD`;
- fall back to curl;
- fall back to size checks;
- treat browser challenge responses specially for known CDN cases;
- preserve previous records when a full re-probe is not due.

An APK is generally treated as usable only when the detected object looks like
an APK and its size is larger than a small threshold. Historical records can be
kept even when the current URL is dead.

Android has a separate TTL:

```text
ANDROID_APK_REPROBE_TTL_HOURS
```

This means Android availability may be newer or older than `url_status.json`.

## HoYo PC Availability

HoYo PC metadata is generated by:

```text
scripts/sync_hoyofiles.py
```

HoYo now uses:

```text
docs/data/hoyo/games.json
docs/data/hoyo/versions/{game}/{version}.json
docs/data/hoyo/chunk/{game}_{version}.json
```

The frontend availability marker for HoYo is based on `unavailable_items` in
`games.json`.

Today, `unavailable_items` is computed from version metadata by counting
download items whose size is `0` or missing. It is not a fresh HTTP probe of
every package URL.

This is useful as a source-metadata warning, but it should not be described as
"the server was just probed and returned 404".

HoYo also has `fetch_head_metadata()` helper logic for reading headers such as
`Last-Modified` and `Content-Length`, but that helper is not the same thing as
the cross-cutting URL health probe.

## WuWa PC Availability

WuWa PC metadata is generated by:

```text
scripts/sync_wuwa.py
scripts/import_tomyjan_wuwa.py
```

WuWa stores selected version metadata in:

```text
docs/data/wuwa/index.json
docs/data/wuwa/versions/{version}.json
docs/data/wuwa/lists/
```

WuWa records can include:

- a primary `url`;
- a `urls` array with multiple CDN candidates.

The current cross-cutting health probe sees the primary `url`, but not every URL
inside `urls`.

The migrated WuWa availability path stores every candidate in the canonical
`availability.candidates` array. The structural pass uses
`source.kind=metadata_inference`; the live canary pass uses
`source.kind=live_probe` for the selected version. Live probing is deliberately
bounded: probe the primary URL first, stop immediately when it is usable, and
only probe backup CDNs after a primary failure. Full-version rollout is kept as
a separate step after canary review.

WuWa also has its own `fetch_head_metadata()` helper for header metadata. It is
similar in name to HoYo's helper but is not a shared implementation.

## Endfield PC Availability

Endfield metadata is imported by:

```text
scripts/import_endfield_archive.py
```

Endfield records use fields such as:

```text
official_url
official_available
mirror_url
preferred_url
```

`official_available` comes from the upstream archive or mirror metadata. It is
not necessarily a live probe performed by this repository at page load time.

The frontend uses `official_available` to label official links as currently
known, expired, or backed by a mirror.

## Arknights PC Availability

Arknights PC currently has a small aggregate data set:

```text
docs/data/arknights/index.json
docs/data/arknights/versions.json
```

Its package URLs are included in the cross-cutting health index, but the page
does not use `url_status.json` to decide whether to show the package records.

## NTE Availability

NTE has separate ResList probing tools:

```text
scripts/probe_reslists.py
scripts/nte_downloader.py
```

These scripts probe versioned resource list archives and build per-version URL
lists. Their availability model predates the newer split-validator pattern.

NTE URLs are also included in the cross-cutting health index through the
generated JSON files.

## Frontend Availability Display

The frontend currently reads availability from game-specific fields:

- Android: `unavailable_count`
- HoYo: `unavailable_items`
- Endfield: `official_available`
- Legacy candidates: `current.status_code` and `archive.status_code`

It does not read `outputs/url_status.json`.

This is why the same UI label can currently mean different things depending on
which game is active. That is the main architecture risk.

## Current Risks

The current system has several drift risks:

- Similar helper names hide different behavior, especially
  `fetch_head_metadata()`.
- Some fields represent live HTTP checks, while others represent upstream
  archive state or metadata inference.
- `url_status.json` can become stale after data-shape changes.
- Multi-CDN arrays such as WuWa `urls` are not fully represented in the
  cross-cutting health index.
- Frontend labels compress different meanings into short labels such as
  "expired" or "unavailable".
- Validators check game data shape, but not availability semantics.

## Rewrite Direction

The next rewrite should use one shared availability model.

The important distinction is: rules do not have to be identical, but the
pipeline and contract must be identical. Android really does need APK-specific
size and content-type checks. Endfield really does need official-versus-mirror
preference rules. WuWa really does need multi-CDN selection rules. Forcing
those rules to be textually identical would create a new failure mode.

What must be unified is the shape:

- every game enters the same probe pipeline;
- every game receives the same probe facts;
- every game exposes the same interpretation fields;
- every frontend view reads the same availability contract.

The target flow should be:

```text
raw URL candidate set (1..N URLs)
  -> canonical probe result set
  -> game/source-specific interpretation
  -> frontend display label
```

In other words:

1. First make an overall judgment about the URL object itself.
2. Then make a secondary judgment based on game/source rules.
3. Store both judgments explicitly.

Do not let each game invent its own meaning for the same field names.

The first layer is the only layer allowed to perform network I/O. It answers:
"What is the current observed state of this URL object?" It must not know about
APK rules, mirror rules, HoYo package semantics, or frontend labels.

The second layer is the game adapter. It answers: "Given the shared probe facts
and this game's source record, how should the project interpret the URL?" It
may apply game rules, but it must not perform HTTP requests.

The probe contract must accept a candidate set, not only a single URL. A normal
package may have one candidate. WuWa can have a primary `url` plus several CDN
entries in `urls`. The probe layer must return facts for every candidate so the
WuWa adapter can choose `preferred_url` without performing network I/O.

Adapters run during data generation or sync, not in the browser. Their output is
written into JSON. The frontend should have no game-specific availability
logic; it should render the precomputed interpretation.

## Proposed Canonical Fields

Future records should separate probe facts from interpretation:

```json
{
  "url": "https://example.invalid/file.apk",
  "availability": {
    "candidates": [
      {
        "url": "https://example.invalid/file.apk",
        "probe": {
          "ok": false,
          "status": 404,
          "method": "HEAD",
          "checked_at": "2026-07-06T00:00:00Z",
          "size": 0,
          "content_type": "",
          "error": "HTTP 404"
        }
      }
    ],
    "source": {
      "kind": "live_probe",
      "confidence": "high"
    },
    "interpretation": {
      "state": "unavailable",
      "reason": "http_404",
      "preferred_url": "",
      "retained": false,
      "display_label": "链接失效"
    }
  }
}
```

The exact schema can change, but these concepts should stay separate:

- probe facts;
- source of the facts;
- confidence;
- game-specific interpretation;
- frontend label.

`state` and `display_label` must stay separate. `state` is machine semantics
such as `available`, `unavailable`, `mirror_only`, or `unknown`. `display_label`
is human-facing copy such as `链接失效`. Scripts and validators should read
`state`; the frontend should render `display_label`.

Historical dead links must be first-class. If a record is intentionally kept for
archive value after it becomes unavailable, set `interpretation.retained` to
`true` and use a reason such as `retained_historical`.

## Closed Availability Vocabularies

These vocabularies should be closed sets. Adapters must not invent new values
without updating this document and the availability validator.

`source.kind`:

- `live_probe`: this repository probed the URL.
- `upstream_archive`: an external archive or mirror supplied the status.
- `metadata_inference`: availability was inferred from source metadata.
- `manual_seed`: a manually curated record is being preserved.

`confidence`:

- `high`: fresh live probe or highly reliable upstream status.
- `medium`: stale-but-recent probe, mirror-backed status, or strong metadata.
- `low`: old probe, weak metadata, or manually retained historical record.

`interpretation.state`:

- `available`: preferred URL is currently usable.
- `unavailable`: no usable URL is known.
- `mirror_only`: original URL is unavailable, but a mirror is usable.
- `unknown`: not enough fresh evidence to decide.

Historical dead links are not a separate state. They should use
`state=unavailable`, `retained=true`, and `reason=retained_historical`.

`interpretation.reason`:

- `http_2xx`
- `http_3xx`
- `http_403`
- `http_404`
- `http_5xx`
- `http_timeout`
- `dns_error`
- `tls_error`
- `range_probe_ok`
- `bot_challenge`
- `size_zero`
- `content_type_mismatch`
- `metadata_size_missing`
- `mirror_fallback`
- `multi_cdn_preferred`
- `upstream_marked_unavailable`
- `retained_historical`
- `not_probed`

## Proposed Shared Probe Module

Create one shared module, for example:

```text
scripts/url_probe.py
```

It should be stateless. It should own only probe primitives:

- request headers;
- URL encoding;
- `HEAD` probing;
- ranged `GET` fallback;
- curl fallback if still needed;
- status normalization;
- content length extraction;
- bot challenge classification;
- timeout handling;
- stable output schema.

It should accept `1..N` URL candidates and return `1..N` candidate probe
results. It should not decide TTL, rotation, batching, or force-full behavior.

Game sync scripts should call this module instead of copying probe logic.
Game adapters must not call curl, `urllib`, `fetch`, or any other HTTP client.
If an adapter needs more facts, the shared probe result schema should be
extended instead.

## Proposed Probe Scheduler

Scheduling and caching should be separate from `scripts/url_probe.py`.

Create a scheduler/cache layer, for example:

```text
scripts/probe_scheduler.py
```

It should own:

- TTL policy;
- failed-record retry windows;
- rotation batches;
- `URL_STATUS_FORCE_FULL`;
- per-source overrides such as Android APK re-probe TTL;
- reuse of previous probe facts;
- stale confidence downgrade.

Android's `ANDROID_APK_REPROBE_TTL_HOURS` should become a scheduler parameter,
not a separate probing implementation.

Staleness must affect interpretation. A stale successful probe should not stay
`confidence=high` forever. Suggested defaults:

- fresh within TTL: keep `confidence=high`;
- older than TTL but within a longer grace window: downgrade to
  `confidence=medium`;
- older than the grace window: downgrade to `confidence=low` or allow the
  adapter to return `state=unknown`.

## Proposed Game Adapters

After a shared probe result exists, each game should only provide an adapter:

```python
class GameAvailabilityAdapter(Protocol):
    game: str

    def interpret(self, probes: list[ProbeResult], record: dict) -> Interpretation:
        ...
```

Every adapter receives the same inputs:

- the canonical probe facts for all URL candidates;
- the original game/source record.

Every adapter returns the same `Interpretation` shape:

- `state`;
- `reason`;
- `preferred_url`;
- `confidence`;
- `retained`;
- `display_label`.

- Android adapter: APK-specific size/content-type rules.
- HoYo adapter: package/update item interpretation and size metadata fallback.
- WuWa adapter: primary URL plus optional CDN alternatives.
- Endfield adapter: official URL versus mirror URL preference.
- Arknights adapter: package URL interpretation.
- NTE adapter: ResList/object URL interpretation.

Adapters should not perform unrelated HTTP logic. They should interpret a shared
probe result.

Frontend code should eventually read only the unified availability contract.
Legacy fields such as `unavailable_count`, `unavailable_items`,
`official_available`, and `status_code` should either be translated by a
compatibility layer or removed after the migration.

## Safe Migration Plan

Do not rewrite everything at once.

Use this order:

1. Document current behavior. This file is that step.
2. Add a read-only availability validator.
3. Define closed vocabularies for `source.kind`, `confidence`, `state`, and
   `reason`.
4. Define the `ProbeResult` and `Interpretation` schemas, including multi-URL
   candidate sets.
5. Define the adapter interface.
6. Refresh `url_status.json` after the HoYo split.
7. Add stateless `scripts/url_probe.py` without changing existing sync behavior.
8. Add the scheduler/cache layer without changing existing sync behavior.
9. Port one low-risk pipeline to the shared module.
10. Compare old and new output side by side.
11. Only then switch the formal data output.
12. Repeat one game/source at a time.

Recommended first adapter target:

- Arknights PC if you want the smallest data surface.
- Android if you want to fix the messiest and most user-visible logic first.

The safer migration order is:

1. Arknights PC, because the data surface is smallest.
2. Android, because it is the messiest and most user-visible.
3. HoYo.
4. Endfield.
5. NTE.
6. WuWa multi-CDN availability last.

Do not start with WuWa file lists unless the goal is specifically to redesign
multi-CDN availability. WuWa's `urls` selection should be treated as its own
design step, not as a casual probe refactor.

## Minimum Checks For Availability Changes

The read-only availability validator should assert:

- every migrated record has an `availability` block;
- every availability block has `candidates`, `source`, and `interpretation`;
- every candidate has `url` and `probe`;
- `source.kind`, `confidence`, `interpretation.state`, and
  `interpretation.reason` are in the closed vocabularies;
- `interpretation.display_label` exists whenever `state` exists;
- `interpretation.preferred_url` is empty or matches one of the candidate URLs
  or a declared mirror URL;
- `interpretation.retained` is boolean;
- retained records use an explicit retained reason;
- stale probes have downgraded confidence or `state=unknown`;
- URL health source files point to existing files.

Any future availability rewrite should run:

```bash
node --check docs/app.js
python scripts/validate_wuwa_split.py
python scripts/validate_hoyo_split.py
python scripts/validate_endfield_archive.py
python scripts/validate_arknights_pc.py
```

It should also verify locally that:

- all 15 game entries render;
- Android / Arknights / WuWa / HoYo / Endfield entries are still present;
- HoYo version shards still load;
- availability labels still match the intended meaning;
- generated URL health source files still point to existing files.
